Part 1

The tiny tool category

~0:10.

Definition

What counts as tiny

One user (you). One problem. One file if possible.
No accounts. No server. No other people's data.

The definition is also the safety envelope.

Real examples

Tools students actually use

Moodboard prompt generator (today's demo) · export checklist app · riso separation previewer · commission price calculator · crit-notes formatter

"Boring-sounding tools get used; impressive-sounding ones don't." Returns in the lab.

Why tiny

Where artists win

Single-file HTML: runs in any browser · can't touch anything else · fully inspectable

Most reliable zone for AI coding. Lowest risk. Yours.

"We stay in this category today on purpose."

Part 1, continued

Spec-first: the interview method

~0:20.

The method

Don't start with "build me an app"

Start with: make it interview you.
One question at a time, max 6.

Your answers become the spec.

Same interview move as Week 6 (characters) — name the rhyme.

The spec

The load-bearing parts

User · problem (with honest frequency) · inputs ≤6 · outputs · UI in words

What it does NOT do — the feature-creep fence
Acceptance checks — 3–5 testable sentences

Template: tiny-tool-spec-template.md. NOT-list and checks are where specs earn trust.

Career note

The professional sentence

"Wrote the spec, directed the build, verified the result."

Current, honest, hireable.

Returns in Week 13 as CV language.

Part 1, continued

The build loop

Client-revision thinking

~0:30.

The build

One prompt builds the file

Spec + "single self-contained HTML file, no frameworks, no build step, no network calls, mobile-friendly."

Save as .html. Open in browser. Working software.

Announce the TextEdit plain-text trap here, preemptively, kindly.

Revisions

Revise like a client, not a coder

Change request: the outcome — "the Copy button should visibly confirm."

Bug report: steps + symptoms — "when the mood field is empty, the output says 'undefined'."

"Same spirit as Blender's error loop. You report; it repairs."

Part 1, the trust layer

Inspection

~0:36.

No programming needed

Three questions

"Walk me through this file like I'm an artist:
what are the three main parts,
where does my data go when I type it,
and does anything leave my computer?"

The week's most important slide. True tiny tool answer: "nothing leaves your machine."

And verify

Check the claim

Skim the file for fetch or http. Ten seconds.

Privacy became checkable the day software became readable conversation.

Do this live in the demo. It lands.
The rule

Boundaries

The scope fence

The moment a tool needs accounts · payments · other people's data — it's not a tiny tool.

App builders will build past the fence. The fence doesn't move.

The inspection

Three questions, then the proof

Scroll the file once — where's fetch? where's http?
Nothing leaves the machine.

"You don't have to read it all. You have to know its shape and where your data goes."
Demo · move 5

The planned failure

The change request broke something. Good.

Bug report, client voice: "when I [steps], it [symptom] instead of [expected]."

Describe the bug, not the code.

If nothing broke, pick a request likely to break. The repair landing is the confidence moment.

Lab · step 1

10 min

Friction hunt

Three recurring annoyances from your actual practice.
Pick the one with the most honest frequency. Write the number down.

The boring candidate beats the impressive one.

"What did you retype, re-look-up, or recalculate this week?"
Lab · step 2

25 min

Interview + spec

Run the interview. Fill the template completely — NOT-list and acceptance checks are where specs earn trust.

✏️ the decisions only you could make.

Circulate: "What should it never do?" "Read me check #2 — is it testable?"
Lab · step 3

20 min · bonus round

Build it

Build prompt → save .html → open → run YOUR acceptance checks.

No build? Spec + build prompt is the full deliverable.
Specifying isn't delegable. Building is.

Chat route works for everyone. Watch for the TextEdit trap.
Lab · step 4

15 min
